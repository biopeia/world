# World

Incremental Biopeia World extraction. This repository currently contains a bounded, transport-neutral causal journal and a minimal synchronous causal coordinator; it is not yet a complete World runtime.

`WorldRuntime` coordinates one active presence and an opaque transition callback. It invokes the callback for the proposed tick, then appends one committed causal record. Only one tick may be in progress: concurrent or reentrant calls fail fast with `TickInProgressError` before invoking their callback and do not change runtime status. If the callback or append fails, the runtime enters `RECOVERY_REQUIRED` and refuses further ticks. The callback runs before publication; it may already have mutated participant state when it fails, and this prototype performs no rollback or recovery.

The journal/runtime coordinate World-scoped causal records without owning Organism-private state, Embodiment somatic state, or Environment state. Event types are opaque here: this package does not define which authority owns their semantics. IDs and tick numbering are deterministic; there is no RNG or host-clock dependency.

`DurableWorldRuntime` is the supported causal commit authority and composes the private, read-only-facing manifest persistence handle with a durable immutable journal-prefix store and an owner-checkpoint writer/verifier callback. Before the callback may persist a proposed causal tick, World publishes `PREPARING` while preserving the last committed refs and proposed roster; callback or startup detection of an interrupted transition latches `RECOVERY_REQUIRED`. It moves the durable manifest through `PREPARING` to `COMMITTED` only after the callback returns opaque owner references, the dependency verifier accepts them, each registered owner codec validates its exact bytes, and the journal prefix is durable. World checks the checkpoint digest and accepts it only when its registered owner codec returns literal `True`; this is an in-process validation gate, not a receipt or independently verifiable attestation. Schema v4 binds commit identity, active presence IDs, exactly one registered `(owner_id, owner_identity)` link per active presence, registered owner identities, and step-only participants. Registration and unregistration of presences and causal owners are explicit per-tick World transitions; commit rejects callback refs that do not exactly match the World-prepared owner and presence rosters.

The manifest store exposes no supported public mutation API: its underscored mutators are internal persistence operations used by `DurableWorldRuntime`; callers must use the runtime for World genesis, lifecycle, transition, and commit. This is API-boundary hardening against accidental bypass, not isolation from arbitrary in-process code or direct filesystem access.

This remains a bounded coordinator, not a general crash-recovery protocol. `recover_previous_cut` is an explicit, caller-authorized rollback to the last committed cut: it verifies that cut's owner checkpoint references and journal, delegates restoration opaquely to owner callbacks, re-verifies the references, writes an immutable recovery receipt for the rollback operation, then republishes that prior cut as `COMMITTED`. Normal `restore` similarly verifies references before and after delegated owner restoration and returns no runtime if the dependency closure changes during restoration. The owner restorer must be retry-safe because a partial restoration may leave `RECOVERY_REQUIRED` set during explicit recovery. If owner restoration or publication fails, callers must handle the failure explicitly; this check does not create a general persistent recovery marker for normal `restore`. Each initial or newly registered owner supplies an owner-codec validation capability. World reads and hash-checks the referenced bytes and asks the owner codec to validate identity and schema; that validation result is not materialized as a per-owner receipt. The initial roster comes from an accepted `WorldGenesisSpec`. The owner component is trusted code: a positive return is not a signed or independently verifiable attestation and cannot prove semantic completeness or storage behavior against a malicious adapter. Schema v4 durably records the active presence roster and its explicit owner association; `PresenceId` is distinct from owner identity, one owner may be linked to multiple presences, and no implicit many-to-many relation is supported. Each runtime still has one actor presence, which cannot unregister itself during its own tick. POSIX advisory file locking serializes store operations on supported local filesystems, but does not establish distributed/multi-host coordination or behavior on every filesystem. A bounded subprocess test now terminates after durable `PREPARING` publication and verifies that reopen identifies the prior committed cut as requiring explicit recovery. A second bounded test terminates during a partial write of the `PREPARING` manifest temporary file, before `fsync` or atomic replacement, and verifies that the previous committed manifest remains recoverable. A third terminates during a partial candidate journal temporary-file write, before `fsync` or hard-link publication; reopen requires explicit recovery of the previous cut, while the partial temp and candidate owner file remain. These are process-termination tests on the exercised local filesystem, not power-loss/storage-device testing, owner-checkpoint write interruption, all journal publication boundaries, multi-writer evidence, orphan cleanup, or a general crash-consistency guarantee; platform durability behavior and full AD-0019 compliance remain unverified.

Tick-zero initialization uses atomic no-overwrite publication. Subsequent manifest operations use a POSIX advisory writer lock plus atomic replacement. This is a single-logical-writer protocol, not distributed consensus.

During a durable tick, a participating owner may contribute opaque `OwnerCausalRecord` values. World binds each record to the current World/tick and the exact participating `(owner_id, owner_identity)`, rejects duplicate stable record identities within the World, and stores the records in the same immutable journal prefix referenced by the committed manifest. Payloads must be strict JSON objects and are detached before publication. World does not interpret the payload or claim scientific custody; the contributing owner retains those responsibilities. This proves durable identification alongside the committed cut under the existing bounded local persistence contract, not independent proof of owner semantics or power-loss durability.

See [`MIGRATION.md`](MIGRATION.md) for exact source provenance, dispositions, validation scope, and deferred responsibilities.


**Durability boundary:** World can persist and hash-check opaque checkpoint references through the supplied verifier, and delegates restoration to supplied owner callbacks. A registered owner codec validates the encoded owner identity and schema; World accepts a literal `True` result and repeats owner validation after delegated restoration. This is a trusted in-process owner contract, not an independently verifiable attestation. It still cannot independently prove that the adapter is honest, that the declared initial roster includes every real authority, or that underlying storage survives actual process/power loss. This implementation must not be treated as full operational durable owner-closed conformance until canonical Biopeia owner implementations are bound through this contract and their integration is independently verified.

## Cross-repository integration tests

`tests/integration` holds the versioned evidence that World coordinates the other authorities in one causal step: the first causal tick, publication and restore of an owner-checkpoint closure, and the first end-to-end physical causal step (`tests/integration/physical_step`). They import `organism`, `embodiment`, `environment` and `observation`; the World package itself depends on none of them.

```sh
python -m pip install -e '.[integration]'   # pinned revisions of the other repositories
python -m pytest tests/integration
```

The default `python -m pytest` run does not collect them. The pins in the `integration` extra are the exact revisions the tests were verified against; a newer revision of another repository is not covered until the pin is moved and the tests rerun. Passing them shows the bounded composition they exercise. It is not a claim of physical calibration, solver equivalence, crash consistency or conformance with the target architecture.
