# World

Incremental Biopeia World extraction. This repository currently contains a bounded, transport-neutral causal journal and a minimal synchronous causal coordinator; it is not yet a complete World runtime.

`WorldRuntime` coordinates one active presence and an opaque transition callback. It invokes the callback for the proposed tick, then appends one committed causal record. Only one tick may be in progress: concurrent or reentrant calls fail fast with `TickInProgressError` before invoking their callback and do not change runtime status. If the callback or append fails, the runtime enters `RECOVERY_REQUIRED` and refuses further ticks. The callback runs before publication; it may already have mutated participant state when it fails, and this prototype performs no rollback or recovery.

The journal/runtime coordinate World-scoped causal records without owning Organism-private state, Embodiment somatic state, or Environment state. Event types are opaque here: this package does not define which authority owns their semantics. IDs and tick numbering are deterministic; there is no RNG or host-clock dependency.

`DurableWorldRuntime` is the supported causal commit authority and composes the private, read-only-facing manifest persistence handle with a durable immutable journal-prefix store and an owner-checkpoint writer/verifier callback. Before the callback may persist a proposed causal tick, World publishes `PREPARING` while preserving the last committed refs and proposed roster; callback or startup detection of an interrupted transition latches `RECOVERY_REQUIRED`. It moves the durable manifest through `PREPARING` to `COMMITTED` only after the callback returns opaque owner references, the dependency verifier accepts them, each registered owner codec validates its exact bytes, and the journal prefix is durable. World checks the checkpoint digest and accepts it only when its registered owner codec returns literal `True`; this is an in-process validation gate, not a receipt or independently verifiable attestation. Schema v4 binds commit identity, active presence IDs, exactly one registered `(owner_id, owner_identity)` link per active presence, registered owner identities, and step-only participants. Presence registration/removal requires an explicit `PresenceLifecycleTransition` validated and committed by World; each committed post-genesis roster change advances one tick and stores a replayable World-authoritative event with separate trigger provenance and the affected owner's checkpoint reference. A last-presence removal leaves an active committed World with zero presences, and later re-entry is supported without a synthetic actor. This implementation does not support ordinary causal cuts with no owner participants: adding persistent World-owned runtime state as a participant requires a separately established contract. Commit rejects callback refs that do not exactly match the World-prepared owner and presence rosters.

The manifest store exposes no supported public mutation API: its underscored mutators are internal persistence operations used by `DurableWorldRuntime`; callers must use the runtime for World genesis, lifecycle, transition, and commit. This is API-boundary hardening against accidental bypass, not isolation from arbitrary in-process code or direct filesystem access.

This remains a bounded coordinator, not a general crash-recovery protocol. `recover_previous_cut` is an explicit, caller-authorized rollback to the last committed cut: it verifies that cut's owner checkpoint references and journal, delegates restoration opaquely to owner callbacks, re-verifies the references, writes an immutable recovery receipt for the rollback operation, then republishes that prior cut as `COMMITTED`. Normal `restore` similarly verifies references before and after delegated owner restoration and returns no runtime if the dependency closure changes during restoration. The owner restorer must be retry-safe because a partial restoration may leave `RECOVERY_REQUIRED` set during explicit recovery. If owner restoration or publication fails, callers must handle the failure explicitly; this check does not create a general persistent recovery marker for normal `restore`. Each initial or newly registered owner supplies an owner-codec validation capability. World reads and hash-checks the referenced bytes and asks the owner codec to validate identity and schema; that validation result is not materialized as a per-owner receipt. The initial roster comes from an accepted `WorldGenesisSpec`. The owner component is trusted code: a positive return is not a signed or independently verifiable attestation and cannot prove semantic completeness or storage behavior against a malicious adapter. Schema v4 durably records the active presence roster and its explicit owner association; `PresenceId` is distinct from owner identity, one owner may be linked to multiple presences, and no implicit many-to-many relation is supported. `WorldRuntime` remains a one-actor prototype; `DurableWorldRuntime` can coordinate a World with no active presence for explicit lifecycle transitions, but does not permit ordinary ownerless causal cuts. POSIX advisory file locking serializes store operations on supported local filesystems, but does not establish distributed/multi-host coordination or behavior on every filesystem. Bounded subprocess tests terminate after durable `PREPARING` publication, during partial manifest-temp writing, during partial journal-temp writing, at the candidate journal file-`fsync` call after its complete payload has been written and flushed, after that candidate file `fsync` returns successfully but before hard-link publication, and immediately after hard-link publication but before the directory-`fsync` call. A separate-process read test observes the `PREPARING` manifest while the single writer is paused inside its owner callback; the original writer then commits. This is read-only visibility evidence and does not establish multi-writer coordination, concurrent recovery, or cross-process crash handling. A separate subprocess also exits after its owner callback writes only a prefix of a candidate checkpoint; the callback never returns a reference and the candidate is not fsynced or adopted. The termination tests verify the old cut remains the committed cut and that the pending transition requires explicit recovery to restore it. For the post-link case, the candidate journal path is visible on the exercised filesystem; this is not evidence that its directory entry survives power loss. These are process-termination tests on the exercised local filesystem, not power-loss/storage-device testing, owner-checkpoint durability, failure during directory `fsync`, concurrent second-process mutation/recovery, multi-writer evidence, orphan cleanup, or a general crash-consistency guarantee; the partial owner-callback write is not an `fsync`/survival test, and platform durability behavior and full AD-0019 compliance remain unverified. A separate injected exception at the journal-directory-fsync boundary verifies that the World runtime enters recovery-required state and retains the previous committed cut after the candidate journal link is visible. The injection occurs before the underlying directory `fsync` call and does not simulate a real OS `fsync` error or power loss.

Tick-zero initialization uses atomic no-overwrite publication. Subsequent manifest operations use a POSIX advisory writer lock plus atomic replacement. This is a single-logical-writer protocol, not distributed consensus.

During a durable tick, a participating owner may contribute opaque `OwnerCausalRecord` values. World binds each record to the current World/tick and the exact participating `(owner_id, owner_identity)`, rejects duplicate stable record identities within the World, and stores the records in the same immutable journal prefix referenced by the committed manifest. Payloads must be strict JSON objects and are detached before publication. World does not interpret the payload or claim scientific custody; the contributing owner retains those responsibilities. This proves durable identification alongside the committed cut under the existing bounded local persistence contract, not independent proof of owner semantics or power-loss durability.

See [`MIGRATION.md`](MIGRATION.md) for exact source provenance, dispositions, validation scope, and deferred responsibilities.


**Durability boundary:** World can persist and hash-check opaque checkpoint references through the supplied verifier, and delegates restoration to supplied owner callbacks. A registered owner codec validates the encoded owner identity and schema; World accepts a literal `True` result and repeats owner validation after delegated restoration. This is a trusted in-process owner contract, not an independently verifiable attestation. It still cannot independently prove that the adapter is honest, that the declared initial roster includes every real authority, or that underlying storage survives actual process/power loss. This implementation must not be treated as full operational durable owner-closed conformance until canonical Biopeia owner implementations are bound through this contract and their integration is independently verified.

## Optional MuJoCo numerical executor

`world.adapters.mujoco.execute_mujoco_step` is an optional, engine-specific
numerical executor (`pip install 'world[mujoco]'`). The caller supplies an
already compiled `mujoco.MjModel` and explicit `qpos`, `qvel`, and `ctrl`
vectors. The function advances one step and returns an immutable candidate
correlated to the supplied `PhysicalStepContext`.

This is not a Biopeia physical-scene schema or a complete production causal
step. Model assembly and owner projections/adoption remain outside the adapter;
the adapter does not mutate or persist owner state, validate authorization,
split results between Embodiment and Environment, or commit a World cut. The
caller is responsible for declaring and correlating the model's effective
timestep and solver settings; the adapter verifies only a positive effective
timestep, not how it was configured. Callers must reject projections they
cannot represent and resolve stable identities, units, and frame semantics
before mapping values to MuJoCo-native vector positions. An explicit
control vector is mandatory; this API does not infer commands for omitted
channels. MuJoCo remains an optional numerical substrate, not a semantic
authority. No calibration or physical-equivalence claim is made.

## Cross-repository integration tests

`tests/integration` holds the versioned evidence that World coordinates the other authorities in one causal step: the first causal tick, publication and restore of an owner-checkpoint closure, and the first end-to-end physical causal step (`tests/integration/physical_step`). They import `organism`, `embodiment`, `environment` and `observation`; the World package itself depends on none of them.

```sh
python -m pip install -e '.[integration]'   # pinned revisions of the other repositories
python -m pytest tests/integration
```

The default `python -m pytest` run does not collect them. The pins in the `integration` extra are the exact revisions the tests were verified against; a newer revision of another repository is not covered until the pin is moved and the tests rerun. Passing them shows the bounded composition they exercise. It is not a claim of physical calibration, solver equivalence, crash consistency or conformance with the target architecture.

The `integration` CI job is required and never silently skipped. It requires the repository variable `CI_READ_APP_ID` and secret `CI_READ_APP_PRIVATE_KEY` so it can install pinned private-repository dependencies. Missing configuration fails the job with a value-free error before token creation; credentials are never printed. Configure both on the canonical repository. Forks without these credentials will show an explicit failed integration check rather than a false green result.
