# World

Incremental Biopeia World extraction. This repository currently contains a bounded, transport-neutral causal journal and a minimal synchronous causal coordinator; it is not yet a complete World runtime.

`WorldRuntime` coordinates one active presence and an opaque transition callback. It invokes the callback for the proposed tick, then appends one committed causal record. Only one tick may be in progress: concurrent or reentrant calls fail fast with `TickInProgressError` before invoking their callback and do not change runtime status. If the callback or append fails, the runtime enters `RECOVERY_REQUIRED` and refuses further ticks. The callback runs before publication; it may already have mutated participant state when it fails, and this prototype performs no rollback or recovery.

The journal/runtime coordinate World-scoped causal records without owning Organism-private state, Embodiment somatic state, or Environment state. Event types are opaque here: this package does not define which authority owns their semantics. IDs and tick numbering are deterministic; there is no RNG or host-clock dependency.

`DurableWorldRuntime` composes the manifest store with a durable immutable journal-prefix store and an owner-checkpoint writer/verifier callback. Before the callback may persist a proposed causal tick, World publishes `PREPARING` while preserving the last committed refs and proposed roster; callback or startup detection of an interrupted transition latches `RECOVERY_REQUIRED`. It moves the durable manifest through `PREPARING` to `COMMITTED` only after the callback returns opaque owner references, each registered owner checkpoint contract returns a typed reference-bound `OwnerRecoveryReceipt`, the dependency verifier accepts them, and the journal prefix is durable. Schema v3 binds commit identity, active presence IDs, registered owner identities, and step-only participants. Registration and unregistration of presences and causal owners are explicit per-tick World transitions; commit rejects callback refs that do not exactly match the World-prepared owner roster.

This remains a bounded coordinator, not a general crash-recovery protocol. `recover_previous_cut` is an explicit, caller-authorized rollback to the last committed cut: it verifies that cut's owner checkpoint references and journal, delegates restoration opaquely to owner callbacks, re-verifies the references, writes an immutable recovery receipt, then republishes that prior cut as `COMMITTED`. Normal `restore` similarly verifies references before and after delegated owner restoration and returns no runtime if the dependency closure changes during restoration. The owner restorer must be retry-safe because a partial restoration may leave `RECOVERY_REQUIRED` set during explicit recovery. If owner restoration or publication fails, callers must handle the failure explicitly; this check does not create a general persistent recovery marker for normal `restore`. Each initial or newly registered owner must be bound to a trusted in-process `OwnerCheckpointContract`; World requires matching owner-generated receipts for recoverability and post-restore verification, bound to owner identity, checkpoint ID, schema, locator, and digest. The owner roster is World-maintained after explicit registration but the initial roster still originates with the runtime initializer. The owner component is trusted code: receipt typing does not cryptographically prove honesty, semantic completeness, or storage behavior against a malicious adapter. The manifest persists and transitions the active presence roster; each runtime still has one actor presence, which cannot unregister itself during its own tick. POSIX advisory file locking serializes store operations on supported local filesystems, but does not establish distributed/multi-host coordination or behavior on every filesystem. Process/power-loss crash consistency and platform durability behavior remain unverified. Do not infer full AD-0019 compliance from these API-level tests.

Tick-zero initialization uses atomic no-overwrite publication. Subsequent manifest operations use a POSIX advisory writer lock plus atomic replacement. This is a single-logical-writer protocol, not distributed consensus.

See [`MIGRATION.md`](MIGRATION.md) for exact source provenance, dispositions, validation scope, and deferred responsibilities.


**Durability boundary:** World can persist and hash-check opaque checkpoint references through the supplied verifier, and delegates restoration to supplied owner callbacks. The runtime requires a registered owner component to issue a typed `OwnerRecoveryReceipt` for each exact checkpoint ref and to verify restoration after the delegated restore. This is an explicit trusted in-process owner adapter contract, not a caller-chosen boolean alone. It still cannot independently prove that the adapter is honest, that the declared initial roster includes every real authority, or that underlying storage survives actual process/power loss. This implementation must not be treated as full operational durable owner-closed conformance until canonical Biopeia owner implementations are bound through this contract and their integration is independently verified; receipt structure alone does not prove the guarantees.
